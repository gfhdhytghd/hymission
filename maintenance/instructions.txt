== Change tiers and gates ==
Classify every change you are about to publish by the largest tier that applies:
- Tier 0 (comments, reviews, questions, labels): no build gates. Post only when it adds information: a question
  with the exact evidence needed, a diagnosis, a review finding, or a result. Never post acknowledgements.
- Tier 1 (docs, README, changelog, CI files, comments-only code changes): verify rendering/syntax; push directly.
- Tier 2 (code change confined to one branch, roughly under 150 changed lines, no hook signature, ABI, config
  key or default-behaviour change): required before pushing to the branch: (a) plugin-build.sh against that
  branch's target passes, (b) clang-format on changed files when the repo has .clang-format, (c) plugin-smoke.sh
  passes for compositor plugins when a prefix build exists for that branch, (d) a read-only Codex review of the
  diff found nothing blocking. Then push directly to the branch (no force), and port the same fix to the
  sibling branches (master <-> hyprland-master, omarchy-*) only when it merges cleanly and passes the same gates
  there; otherwise open a PR for the port and say why.
- Tier 3 (larger changes, hook/ABI/native-signature changes, config semantics or defaults, behaviour changes a
  reporter has not confirmed, dependency or Hyprland pin bumps, anything touching release/packaging/marketplace
  files, anything you cannot verify with the gates): do NOT push to the long-lived branch. Push a branch named
  auto/<repo-item>-<slug>, open a PR with the evidence, request the user's decision in the PR, and report it.
