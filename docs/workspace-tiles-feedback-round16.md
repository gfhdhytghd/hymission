# Stage desktop edge continuity and right-edge overview coverage (FB16)

## Baseline, reproduction and evidence limits

Requested baseline: `5650d1a`. Before final validation this branch was rebased onto `origin/hyprland-master` at `7815b41`, including FB15's native flight endpoints and complete workspace-card apertures. The `hymission-tiles-fb7` worktree is untouched.

The reported static left-edge screenshot is not reproduced by the isolated controls. The 1041461 release-source build, archived FB10/FB11 controls, 7cdc3ed and 5650d1a all render the left desktop band when a native scrolling client crosses it. The controls compare width 32 against width 0 at identical native geometry, rather than interpreting a screenshot's straight crop as proof that the shader was absent. No static-left regression introduction is claimed. The host IPC is unavailable (`HYPRLAND_INSTANCE_SIGNATURE` is unset); the supplied images are read-only inputs, not a reproduced host-session state.

A separate reproducible mismatch exists in workspace-flight rendering: native tiled scrolling desktops soften both horizontal seams, but Stage's desktop flight endpoints retain only the original single-monitor, sidebar-facing edge. An incoming right-side column therefore loses its right band before the final native handoff. FB10 (`f080e8b`) enabled clustered Stage flights by removing the `!clustered` gate while retaining those single-sided endpoints. Diagnostic boundary builds confirm that the parent `7845a3c` has no clustered Stage flight in this route, whereas `f080e8b` produces the one-sided flight. FB11's input changes, FB12's flight paint ordering, FB13's overview reveal and FB14's native viewport resize do not repair that endpoint mismatch. This is an animation-path finding, not proof of the static screenshot's cause.

A diagnostic-only build of exact `7815b41` exposes the already-existing flight viewport widths through IPC. At late phases, its incoming right band approaches zero and actual right-edge marker pixels are opaque green. The repaired endpoint retains a 32-pixel band and the same boundary samples fade to wallpaper while a sample 36 pixels inside remains green. The private controls retain every rendered frame and native/Stage state; `flight-edge-pixels.json` lists the actual witness coordinates, phases and PNG paths.

## Change

`desktopEdgeViewport()` preserves the original sidebar-facing policy with tiles disabled or one tile, and supplies both horizontal bands for clustered tiles. Both the old desktop takeoff endpoint and the current desktop landing endpoint use it; tiled fadeout captures share the same viewport policy. Native work-area reservation, camera rebasing, the FB15 aperture/geometry repair, flight ordering and vertical extents are unchanged. The additive `viewport_edges` IPC field makes the animated aperture auditable. Each screen now samples its flight phase once for all reported window geometries, apertures and `transition_progress`; reading the clock separately could contradict the same JSON snapshot under CPU preemption. This changes diagnostics, not the animation clock or rendering.

The new private `--stage-edge-regression` covers disabled/single/two/three tiles. Fixed native geometry isolates alpha and Gaussian blur: removing the known wallpaper contribution still leaves mixed red/green marker-header pixels with the shader enabled, while the hard-clip control has none. Native scrolling, rather than those fixture placements, supplies the subsequent Stage open/close and workspace-flight recordings. Middle-frame boundary pixels, clear interior pixels and late incoming aperture widths are checked separately. The same checks also hold a real four-finger native workspace gesture at 90% progress: the last tile supplies 9 (two tiles) and 7 (three tiles) actual right-edge pixel samples with clear interiors and faded boundaries.

## Overview's outer right edge

FB13's right-moving band already covers the physical output's right edge. The old paired shadow test, however, scanned only the left side of each window. It now scans both sides of the complete window/shadow footprint outside the moving mask, excluding other windows and requiring identical held geometry. Wholly hidden right-hand windows can expose their left shadow first; restricting the right scan to the window's rightmost few pixels would miss them.

Exact `7cdc3ed` passes the extended control. Two tiles provide 1,152 sampled pixels belonging to windows beyond the rightmost tile's physical right edge; three tiles provide 4,224. No shadow-on/off differences appear outside the moving mask. Zero-sample phase/scope combinations are retained explicitly: for example, the three-tile ws-overview right band can coincide with the output edge, leaving no off-mask pixels inside the framebuffer. Those combinations do not count as pixel proof. No additional overview rendering change is necessary for this finding.
